# Failure modes

Each row says what goes wrong, what the system does, what the client sees, and which spec forces that failure and checks the result. Paths are relative to the repository root. Spec names are the feature names inside the file.

| Failure | What happens | Client sees | Proof |
|---|---|---|---|
| Crash mid-transfer (application process) | An exception after the balances were changed and before commit. The whole transaction rolls back: balances, transfer row, journal and the idempotency claim. | No answer or an error. A retry with the same key moves the money once. | [`FailureModesIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/FailureModesIntegrationSpec.groovy): "crash mid-transfer (application)" |
| Crash mid-transfer (database connection) | The PostgreSQL backend is terminated before COMMIT. The commit fails and the uncommitted debit is never visible. | Error. Safe to retry with the same key. | Same file: "crash mid-transfer (database connection)" |
| Client retry (same key, same body) | The key is already claimed. The stored transfer is returned. | `200`, `Idempotency-Replayed: true`, the original transfer | [`TransferServiceIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/TransferServiceIntegrationSpec.groovy): "retrying with the same key and the same body returns the original transfer and moves money once"; [`ApiIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/ApiIntegrationSpec.groovy): "retrying with the same Idempotency-Key and body returns 200 with the original transfer" |
| Same key, different body | The fingerprint differs, so the retry is refused. Nothing moves. | `409 idempotency_key_reused` | `TransferServiceIntegrationSpec`: "the same key with a different body is a conflict, whichever field differs" |
| Timeout after commit | The transfer committed, the answer was lost. The client cannot tell and retries with the same key. | `200`, replayed, the original transfer. One transfer exists. | `FailureModesIntegrationSpec`: "timeout after commit" |
| Duplicate request (arrives at the same time) | Twenty requests with one key arrive together. The key claim is a primary-key insert; the others wait for the first transaction and then see its result. | One `201`, the rest `200` replays. Exactly one transfer. | `TransferServiceIntegrationSpec`: "twenty parallel requests with the same key create exactly one transfer" |
| Redis down | The velocity limit fails open by default (or refuses, with `VELOCITY_FAIL_OPEN=false`). The idempotency cache is skipped and PostgreSQL decides. | With risk disabled and fail-open enabled: transfers work, health is `degraded`. Fail-closed refuses earlier with `500 internal_error`. With risk enabled and fail-open enabled: see HOLD below. | [`RedisBehaviourIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/RedisBehaviourIntegrationSpec.groovy): "with Redis unreachable, transfers still work, replays still dedupe via Postgres and health is degraded" and "...fail-open disabled, transfers are refused instead of unchecked" |
| Redis wrong (stale or poisoned) | Every replay checks the PostgreSQL key-to-fingerprint-to-transfer binding, regardless of Redis hash or pointer. Forged unclaimed keys cannot replay another transfer. | Correct result, as if the cache were empty. | `RedisBehaviourIntegrationSpec`: "a poisoned cache entry cannot make the API repeat or invent a transfer", "garbage in the cache is ignored" |
| DB down | The pool cannot give out a connection within the timeout (`DATABASE_CONNECT_TIMEOUT_MS`). The error is reported as `storage_unavailable`. No claim is made, so the key is not used up. | `503`, `Retry-After: 1`. `/health` is `503` with `postgres: down`. After PostgreSQL returns, the same key works and the money moves once. | `FailureModesIntegrationSpec`: "database down: requests get 503, nothing moves, and the same Idempotency-Key works after the database is back" |
| Deadlock | Two transactions lock rows in opposite orders and PostgreSQL aborts one with `40P01`. Ordinary strategies and HOLD placement lock/touch both customer accounts in ascending id order, including rows implicitly needed by transfer foreign keys. Deterministic opposite HOLD and mixed ordinary/HOLD cases are covered by `HoldLockRegressionSpec`. If it happens anyway it is translated to `ConcurrentUpdate`. | Retried inside the service, then `409 concurrent_update` if the budget runs out. | `FailureModesIntegrationSpec`: "deadlock: PostgreSQL aborts one transaction with 40P01 and the application reports it as a retryable ConcurrentUpdate"; [`ConcurrencyIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/ConcurrencyIntegrationSpec.groovy): the control that locks in opposite orders on purpose |
| Lost race (optimistic strategy) | The version check finds a newer version. The attempt rolls back, including the key claim, and runs again after a random wait. | Usually nothing: the retry succeeds. After the last attempt, `409 concurrent_update` with `Retry-After`. No money moved. | [`StrategyBehaviourIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/StrategyBehaviourIntegrationSpec.groovy): "optimistic: the service loses one race on purpose, retries once and ends with correct balances" and "...when every attempt loses, the caller gets a ConcurrentUpdate and no money moved" |
| Serialization failure (`40001`) | PostgreSQL aborts a transaction at REPEATABLE READ or SERIALIZABLE. The caller rolls back, waits a random time, runs it again. | In the experiment, nobody gives up and the end state follows the rule. | [`IsolationIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/IsolationIntegrationSpec.groovy): "SERIALIZABLE with retry and jitter"; explained in [isolation.md](isolation.md) |
| Insufficient funds under contention | 300 requests of 1.00 race for an account that holds 100.00. | Exactly 100 succeed, 200 get `422 insufficient_funds`, the balance ends at 0. For every strategy. | [`StrategyStressIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/StrategyStressIntegrationSpec.groovy): "300 requests of 1.00 race for an account holding 100.00" |
| A bug that corrupts balances | The audit compares stored balances with the replayed journal. A naive read-modify-write strategy is caught. | Not a client-facing case. It shows the invariant checks can fail. | [`InvariantSuiteHasTeethIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/InvariantSuiteHasTeethIntegrationSpec.groovy) |
| Unbalanced journal written by a bug | The deferred trigger refuses the commit. | The commit fails and nothing is persisted. | `TransferServiceIntegrationSpec`: "the database refuses an unbalanced journal even if the application writes one" |
| Crash between the hold and the release | A transfer was held (money moved from the sender to the hold account, transfer `PENDING`) and the process dies before anyone decides. Nothing else was pending in memory. | After a restart the transfer is still `PENDING`, the money is in the hold account, and release or reject works. | [`RiskHoldIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/RiskHoldIntegrationSpec.groovy): \"crash between the hold and the release\" |
| Crash in the middle of a release | The payee was credited but the commit never happened. | The whole release rolls back: payee unchanged, transfer still `PENDING`, release can be tried again. | Same file: \"a release that fails halfway rolls back completely and can be tried again\" |
| Two people decide the same hold | Release and reject (and a second release) arrive together. The transfer row is locked; the first to get it wins. | One succeeds. The others get `409 transfer_not_pending`. The money moves once. | Same file: \"two people deciding the same hold at the same moment\" |
| A blocked or step-up payment is retried | The payment was refused before any claim or journal was written. | `403` with reason codes. The idempotency key is not used up, so the same key can be sent again with `stepUpConfirmed`. | Same file: \"BLOCK writes an audit row, moves nothing and leaves the idempotency key free\", \"STEP_UP stops the payment until the customer confirms\" |
| A published rule set file is edited | The stored hash differs from the file. | The application refuses to start. Nothing is decided with rules nobody can trace. | Same file: \"a published rule set version cannot be changed\" |
| Risk audit tampering | An UPDATE or DELETE on a decision, a hit or a rule set. | The database rejects it (`restrict_violation`). | Same file: \"the audit tables refuse updates and deletes\" |

| Redis down during risk assessment | The sliding-window count and amount cannot be read. The risk engine never treats this as zero. | `202 PENDING` with `VELOCITY_UNAVAILABLE`, money parked in the hold account. A replay still deduplicates via PostgreSQL. With the older per-minute throttle set fail-closed, it instead refuses earlier with `500 internal_error`. | [`RiskSignalsIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/RiskSignalsIntegrationSpec.groovy): "risk enabled with Redis down parks money rather than paying unchecked" |

| Crash during feature projection | Feature writes and outbox acknowledgement share a transaction. | All roll back together. The next poll retries; a repeated event does not increment aggregates twice. | [`OutboxIntegrationSpec`](../src/integrationTest/groovy/dev/erencivril/ledger/OutboxIntegrationSpec.groovy): "a projection failure rolls back deduplication, aggregates and acknowledgement together" |
| Poller stopped or slow | The risk read model is behind the ledger. | History includes completed payments not yet projected, so it does not drop facts. Money paths do not wait for the poller. | Same file: "a stalled projection falls back to the ledger for risk facts" |

## Audit commit scope

Immutable account and amount validation runs before either Redis limiter or risk audit writes. BLOCK and unconfirmed STEP_UP commit refusal audits separately without claiming a key. ALLOW/WARN/HOLD decisions commit atomically with the money transaction; later money failures roll them back. Replays and risk-disabled requests create no new decision row. Redis attempt windows are separate side effects, not part of the PostgreSQL transaction.

## What is not covered

- A crash of PostgreSQL itself after it acknowledged a commit but before the disk write is PostgreSQL's durability guarantee (`fsync`, WAL). The specs do not test PostgreSQL's own recovery.
- A network partition between the application and PostgreSQL in the middle of a COMMIT is the "timeout after commit" row: the client cannot know, and the idempotency key is what makes retrying safe. The spec simulates a lost answer, not a real partition.
- Redis returning wrong data is covered. Redis losing data on restart is the same as an empty cache.
